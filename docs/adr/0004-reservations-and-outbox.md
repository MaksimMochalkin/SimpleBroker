# ADR-0004: Cross-module reservations and transactional outbox

**Status:** accepted (stage 2)

## Context

A Buy order must reserve funds in Accounts before Orders persists the order. The modules have separate schemas and contexts; sharing one database transaction across module internals would weaken the modular boundary and make later extraction harder. Domain events must also be delivered without publishing an event for an order or transfer that never committed.

## Decision

- Orders calls the Accounts contract to reserve funds using a reservation identifier generated by Orders. Accounts persists the reservation and adjusts `available`/`reserved` in its own transaction.
- Orders then persists the order and its `OrderCreated` outbox row in the Orders transaction.
- If inserting the order fails after a successful reservation, Orders calls `ReleaseAsync` as a compensating action. Reservation create/release operations are idempotent by reservation ID.
- A Buy Limit reserves `price × quantity`. A Buy Market order requires a caller-supplied price ceiling. Sell orders do not reserve funds in this stage because positions are out of scope.
- Each module writes its event to an outbox table in the same transaction as its business update. A background publisher claims batches with `FOR UPDATE SKIP LOCKED`, sends them to an `IMessageSink`, and records `published_at`.
- Delivery is at least once, not exactly once. Consumers must deduplicate by message ID; ordering between multiple publishers is not guaranteed.
- Keep the reservation-without-order crash window explicit. A reconciler is deferred to the resilience stage; the current compensation only covers a handled insert failure.

## Alternatives considered

- **One transaction spanning Accounts and Orders:** rejected. It couples module persistence internals and works against the schema-per-module boundary.
- **Publish directly before or after a database commit:** rejected. Publishing before commit can expose rolled-back events; publishing after commit can lose events if the process stops between commit and send.
- **Claim outbox rows without `SKIP LOCKED`:** rejected. Multiple publishers would unnecessarily block each other on the same pending rows.
- **Promise exactly-once delivery:** rejected. A process can crash after the sink accepts a message but before `published_at` commits; consumers need idempotency.

## Consequences

- A failed order insert can release the reservation without a distributed transaction, but a process crash between reservation and order persistence can leave reserved funds until reconciliation.
- Events are durable with the business transaction and are retried by the publisher.
- A sink may observe duplicate delivery; message IDs are the idempotency key.
- The current logging sink demonstrates the delivery path but is not a production broker.

## Evidence

The stage 2 integration tests cover reservation amount and insufficient-funds behavior, idempotent reserve/release, event delivery, and two publishers without duplicate sink delivery.
